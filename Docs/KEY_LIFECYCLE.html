The Key Rack

Five distinct secrets, six stages, one file. This traces where each secret is born, where it travels, where it is never written down, and what a recipient is left holding after they are revoked.

The five secrets · state at stage 1 Click any secret for its definition.

    What a capture is actually worth

    The four rows below are the answer to nearly every question an examiner will ask, and the last one is the row to volunteer rather than wait for.

    1. The .sfit file alone Nothing, ever Every slot needs a KEK; every KEK needs two halves; you have neither.
    2. A device share, unsealed Nothing on its own Half a key, with no way to obtain the other half. It decrypts nothing.
    3. An epoch licence share One epoch, one recipient, one device Bounded on three axes at once. Worthless in any other slice.
    4. The CEK, dumped from memory That container — forever Not other containers: each has its own random CEK. Not anyone else's future access: revocation still governs that. But this one document, permanently.

    The hierarchy, as the code writes it

    CEK               = OsRng(32)                       one RANDOM key per container
share_device_r    = OsRng(32), HPKE-sealed to r's device key, lives in the .sfit
share_licence_r_e = HKDF(server_root_cid, "safeit/v1/epoch" ‖ cid ‖ device_id_r ‖ LE64(e))
                    server-side only; server_root_cid NEVER leaves the server
KEK_{r,e}         = HKDF(kdf_salt, share_device_r ‖ share_licence_r_e,
                         "safeit/v1/kek" ‖ cid ‖ recipient_r ‖ LE64(e))
slot_{r,e}        = AEAD(KEK_{r,e}, nonce, aad = cid‖recipient_r‖slot_type‖LE64(e), CEK)
    Never write CEK = HKDF(shares). It reads more elegantly and it silently kills per-recipient revocation: if the CEK were derived from the shares, every recipient would need byte-identical shares to land on the same CEK — so a revoked recipient could be re-admitted by a colleague pasting 32 bytes into a chat window. ADR 0010 was written to retract exactly that.
